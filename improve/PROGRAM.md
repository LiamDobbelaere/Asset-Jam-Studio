# The improvement loop: rules for the agent

You are one iteration of a loop that improves Asset Jam Studio a little at a time. A runner (`improve/loop.py`)
starts you, scores what you changed with a fixed harness, keeps the change only when the track's metric got better
by more than its noise, and starts the next iteration with your notes. Nothing you do is merged into `main` by
itself: everything lands on the branch `improve/<track>`, which a person reviews.

The person owns this file and the track definition. You own the track's playbook (`NOTES.md`), its backlog, the
handoff to the next iteration (`next.md`) and the memory notes you write. Do not edit this file, the runner, the
scorer or the track definition, even when you are sure they are wrong: write what is wrong in `NOTES.md` under
"Harness problems" and the person will fix it.

## One iteration

1. Read the state you are given: the playbook, the backlog, the last results, the handoff from the previous
   iteration, and `memory/MEMORY.md` (open the memories that look relevant; they hold what earlier sessions
   measured and what turned out to be a dead end).
2. Pick ONE hypothesis. The first untried backlog item that the handoff recommends, unless the results since make it
   pointless. A hypothesis says what you change, why it should move the metric, and what you expect to see.
3. Make the change. Only files on the track's editable list; keep it small and self-contained, so the result says
   something about one idea. Reversible by construction: the runner reverts a discarded change with git.
4. Answer with the JSON you are asked for. Do not score the change yourself and do not run the scorer: the runner
   does that, so that the metric is never produced by the same session that made the change.

A second, short session runs after the score is in: it records the result, updates the playbook and the backlog,
writes the handoff for the next iteration and, when the result is something a later session would need to know,
a memory note.

## What counts

- Kept: the metric improved by at least the track's `min_delta`, every guard stayed in range, no prop failed.
  Equal results with less text or simpler code are also worth proposing: the runner does not keep them, but say so
  in the notes and the person may.
- Discarded: everything else. A discard is a result, not a failure: write down what it rules out.
- A small gain that makes the brief or the code harder to follow is not worth it. Prefer removing a rule that
  does not help over adding one.
- Never game the metric: no special-casing the evaluation props, no reading the originals' files, no changing
  which props are scored, no touching the scorer or the renders. The runner hashes the harness and reverts a
  changed one; a change outside the editable list is reverted without being scored.

## Memory

`memory/` is the project's shared memory (rules in `AGENTS.md`). Write one memory file when an iteration teaches
something durable: a measured number, a lever that does nothing, a trap. Not every iteration deserves one; a
result that only matters inside this loop goes in `NOTES.md`. One fact per file, kebab-case name, the frontmatter
`name` / `description` / `metadata.type: project`, then the fact, **Why:** and **How to apply:**, absolute dates,
and one index line in `memory/MEMORY.md`. Update an existing memory rather than adding a near-duplicate. Nothing
that names the private game, its characters, actors or local `D:\...` paths goes in a tracked memory: that belongs
in `memory/private/`.

## Stopping

The runner stops you at the iteration, time and budget limits, when `improve/STOP` exists, or when the person
interrupts. You do not decide to stop; you do not ask whether to continue.
